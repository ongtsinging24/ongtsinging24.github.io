Claude Code：讀懂 statusline、控住成本、協調多個 session

CC 每一輪（包括每一次工具呼叫）都會把整段 context 重送一次。所以輸入框下方那行 statusline 上的 ctx、cache、$ 其實就是成本儀表板。這篇先說明 statusline 怎麼設定、怎麼讀，再拆解高用量成本從哪裡來，最後整理 CC 內建的 session 協調機制：哪些是內建的，哪些要自己補。

成本 ≈ ctx × 輪數 × 單價跟 token 絕對值走，不跟 ctx% 走
cache 命中差 20 倍同樣 120k ctx，全命中 vs 全失效（1h TTL）
協調 = 傳訊 + 通知 + 隔離內建沒有鎖，也沒有 git index 保護

CC

ctx

TTL
time-to-live，prompt cache 的存活時間（5 分鐘或 1 小時）

Remote Control，從手機或網頁遠端操作本機 CC session

worktree

S_1statusline 機制

statusline 是 CC 輸入框下方一行可以自訂的狀態列。CC 把 session 狀態寫成 JSON 從 stdin 傳給你的腳本，再把腳本 stdout 的第一行顯示出來。設定寫在 user 層或 project 層的 settings.json：

"statusLine": {
  "type": "command",
  "command": "python3 ~/.claude/statusline.py",
  "padding": 0
}
  • 也可以在 CC 裡打 /statusline <描述>，由內建的 statusline-setup agent 產生腳本並改好設定
  • 對話狀態一變就更新，但有節流（throttle）
  • 可以用 ANSI 上色。腳本必須跑得快，不要在裡面打網路 API；git 這類呼叫要設 timeout

stdin JSON 常用欄位

欄位內容
model.id / model.display_name目前使用的模型
workspace.current_dir / project_dircwd 與專案根目錄
transcript_path本 session 的 jsonl 對話紀錄（可以讀末筆 usage 當 fallback）
session_id, version, output_style.namesession 與版本資訊
cost.total_cost_usdsession 累計花費（按 API 牌價換算）
cost.total_lines_added / _removed本 session 改動行數
context_window.*（新版才有）used_percentage、context_window_size、current_usage、total_output_tokens

舊版沒有 context_window 時的退路：讀 transcript_path 最後一筆 assistant 訊息的 usage，把三項 input 加總後自己算。欄位不存在的段落要自動隱藏，傳空的 {} 進來也不能報錯。

S_2一行讀懂：每一段在講什麼

下面是一個實際的 statusline 範例，主機與路徑已遮蔽。滑過或點一下任一段，就會標出對應的說明。

user@host:~/project (main) [Opus 5.5] ctx 120.0k 12% cache 100% out 429 $1.96 +0/-0
ctx 120.0k 12%：這一輪送出多少
  • 值 = 最近一次請求的 input + cache_read + cache_creation，也就是下一輪要整包重送的量
  • 120k ÷ 12% ⇒ 1M 窗。沒給 size 時，model id 含 [1m] 或已用量超過 200k 就當 1M，否則當 200k
  • 顏色：<60% 青、60–79% 黃、≥80% 紅（快觸發 auto-compact）
  • 12% 看起來很少，但 120k 本身就是每輪的固定成本。
cache 100%：最近一次的快取命中率
  • cache_read ÷ (cache_read + cache_creation + input)，只看最近一次請求，不是 session 平均
  • 顏色：≥80% 綠、50–79% 黃、<50% 紅
  • 突然掉到紅色 = 快取失效重寫（離開超過 TTL、換模型、改 CLAUDE.md、增減 MCP）。這一輪付的是寫入價，ctx 越大越痛
  • 新 session 第一輪、/compact 後第一輪本來就會偏低，屬正常
out 429：輸出 token
  • 優先取 context_window.total_output_tokens（session 累計），沒有就退最近一則回應的 output_tokens
  • 單價約為 input 的 5 倍，但量通常小；含 thinking token，effort 開高就會漲
  • 本例 429 對比 $1.96：花費幾乎全在 input 側（大 ctx 重送），不是模型話多
$1.96　+0/-0：累計花費與改動行數
  • cost.total_cost_usd：session 累計，按 API 牌價換算。訂閱制（Pro/Max）只是等值估算，不會真的照額扣款；走 API key 或企業按量計費才是真的要付
  • 行數：綠 +N、紅 -N
user@host:cwd (branch) [model]
  • branch 是 cwd 所在 repo 的分支。cwd 在巢狀 repo 裡時，顯示的是那個子 repo 的分支
  • detached HEAD 時顯示 @short-sha；可以加 * 標示工作樹有未提交改動

S_3單輪成本試算

把 ctx、cache 命中率和輸出量合起來，就能估出一輪的成本。單位用「base input token 等值」表示，不寫死美元單價（各模型價格不同，而且會調整）。

單輪 ≈ ctx × [命中率 × 0.1 + (1 − 命中率) × w] ＋ out × 5
w = cache 寫入倍率：5 分鐘 TTL 1.25×，1 小時 TTL 2×；結果乘上 input 單價即為金額
120k
100%
500
—本輪 ≈ base input token 等值
—同 ctx、全命中時
—是全命中的幾倍

成本組成：快取讀取（0.1×）／未命中重寫（w×）／輸出（5×）。拉低命中率，看中間那段怎麼吃掉整條。

例：ctx 120k、命中 100% ⇒ 約 12k 個 base token；同樣 120k 若命中 0%（1h TTL）⇒ 240k，差 20 倍。這就是「離開一小時回來，第一句話特別貴」的原因。

S_4高用量成本的常見成因

核心機制只有一條：CC 每一輪都把整段 ctx 重送一次。

成本 ≈ 每輪 ctx 大小 × 輪數 × 單價（快取命中時便宜，沒命中時貴）

大致依影響排序

#習慣為什麼貴
1ctx 從不清理一個 session 做到底、換題目也不 /clear，1M 窗長到幾十萬 token 還繼續聊。同樣讀一個檔，ctx 20k 和 600k 時成本可差 30 倍
2把大東西倒進 ctx讀整份大檔或完整 log、跑會吐大量輸出的指令。內容進了 ctx 後，每一輪都要再付一次
3快取一直失效超過 TTL 才回來、中途換模型、改 CLAUDE.md 或增減 MCP：整包 ctx 用寫入價重寫
4輪數爆炸短間隔 /loop 輪詢、沒有方向地反覆試錯、headless（claude -p）迴圈沒設上限
5平行化太多同時開很多 session、大量 subagent／workflow fan-out，每個 agent 都有自己的 ctx
6模型和思考強度一律開最高小事也用最大模型加 max effort，產生大量 thinking token
7MCP 工具定義太肥每輪都要送幾萬 token 的工具定義

診斷法

  1. 用 /cost，或用 ccusage 分析 ~/.claude/projects/*/ 下的 jsonl。少數巨大 session 佔大宗 → 第 1、2 項；session 數量非常多 → 第 4、5 項
  2. 拆 usage 欄位：cache_creation_input_tokens 偏高 → 快取失效（第 3 項）；cache_read_input_tokens 很高 → ctx 太大或輪數太多（第 1、4 項）
  3. 自己寫統計腳本時，要用 message.id 去重。jsonl 裡同一則訊息會逐行重覆，不去重約高估 1.8 倍

控管建議

  • 一個任務一個 session，換題目就 /clear
  • ctx 超過約 60% 時先 /compact 或開新 session
  • 大檔只讀需要的段落；log 先用 grep／head／tail 過濾
  • 日常改碼用較小的模型，難題再切大模型
  • 自動化迴圈設輪數上限，不要短間隔輪詢
  • statusline 加上 ctx% 和 $，即時看到花費

S_5session 協調：依「離你多遠」分五層

以下整理自 CC 工具本身的說明（Agent、SendMessage、ListAgents、ReadNotifications、FetchInboxMessage、SendToProject、EnterWorktree、Monitor），不是憑印象寫的。CC 版本會改，實際用之前請再看工具說明。

L1同一 session 內
Agent 開子 agent；fork 複製自己並繼承完整脈絡；SendMessage(to=名字) 叫已結束的子 agent 接著做；背景子 agent 要用 SendMessage(to="main") 回報，它的一般文字輸出母 session 看不到；TaskStop 提早停；Workflow 用腳本確定性編排多個 agent（要 user 明確要求才能用）。
L2同機其他 session
ListAgents 找對象，每列開頭的 name 就是位址；SendMessage 跨 session 傳話；notify_when_idle 一次性訂閱「對方閒置或退出」。細節見 S_6。
L3跨機／雲端／外部
RC 與雲端 session 也在 ListAgents 裡（雲端收得到但不能回信）；ReadNotifications 收 GitHub PR、排程 trigger、其他 session 的訊息；FetchInboxMessage 讀 RC 綁定 chat thread 傳來的訊息；/send-to-project 把工作轉交到雲端 Claude Project；/schedule 建雲端排程 routine。
L4共享狀態
Artifact 的 db capability（多人共讀共寫的小型資料庫）；Artifact 留言 @Claude 可把 session 叫進來處理。
L5隔離與等待
EnterWorktree 或 Agent(isolation="worktree")：每個 session 一個獨立 worktree。等一次就結束用背景 Bash 的 until 迴圈；持續監看用 Monitor（最長 30 分鐘要重新掛上）。

L3 外部管道的方向與信任

機制方向信任等級
ReadNotifications進來參考資訊，不是 user 的指令
FetchInboxMessage進來只有外層標記 from="rc_owner" 才算 user 本人；其他一律視為第三方文字
/send-to-project出去只有 user 親自下指令才能用，送出前有確認畫面
雲端 session出去收得到但不能回信，結果要去它的 transcript 看

S_6跨 session 傳話的六個細節

  1. 回覆要抄 from。對方收到時外面包著 <cross-session-message from="...">；回信時把 from 的值抄進 to。
  2. 送到 ≠ 讀到。訊息排隊，等對方下一個工具回合才處理。
  3. 沒回音不代表同意。對方 permission mode 跟你不同時，訊息要先等對方 user 核准（可能過期），對方也可能拒收。同機會回 delivery notice；RC 與雲端什麼都不回報。
  4. @檔案 不會附檔。在對方那邊只是一般文字，內容要直接寫進訊息。
  5. 等對方做完用 notify_when_idle。一次性訂閱，對方下次閒置或退出時通知你；不帶 message 就是純訂閱，對方零成本。輪詢 ListAgents 或一直問「做完了嗎」都是官方明確不建議的做法。
  6. 權限不能借道。每個 session 的權限各自獨立，禁止叫別的 session 做你這邊被拒絕的動作（cross-session permission laundering）。另外，子 agent 送出的跨 session 訊息用的是母 session 的位址，回信會進母 session。

S_7內建有的 vs 要自己補的

多個 session 在同一個 repo 上並行時，下面這張表是實際踩過的對照。右欄是我自己的多 session 協作規約補上的部分。

需求CC 內建自己補
找到對方ListAgents用 /rename 把 session 改成 branch 名，名字一看就懂
傳話SendMessage共享 md 頻道，可留存、事後回查
等對方做完notify_when_idle不必另做，改用這個取代輪詢
檔案互斥／認領沒有（沒有 lock）認領檔、版號登記、開工前先查 worktree 與他人認領
git index 保護沒有禁 git stash／git add -A（會捲走別人未提交的工作）；逐檔 staging
工作樹隔離worktree注意例外：讀寫固定絕對路徑的流程、測試會讀主樹路徑時，worktree 給的是假結果

結論：CC 內建的是「傳訊 + 通知 + 隔離」這幾樣基本元件，沒有鎖，也沒有共享 index 保護。多個 session 動同一棵工作樹時，認領與 git 紀律仍然要自己守。
